## 2026-08-05 / 2026-08-06
- Wiring finalized: RAK3272S RST -> Pico GPIO2, module UART on Pico UART1/`Serial2` (GPIO4 TX, GPIO5 RX), power from Pico `3V3(OUT)`/GND.
- Dev environment set up directly on `rak-gateway` (it has a desktop, so this was feasible): `arduino-cli`, the `rp2040:rp2040` board core (arduino-pico by Earle Philhower, board `rp2040:rp2040:rpipicow`), VS Code + `vscode-arduino.vscode-arduino-community` extension (Arduino IDE 2.x has no official Linux ARM64 build).
- Wrote and confirmed working: AT-command based OTAA join on boot (region IN865/band 3, class A), with manual AT command passthrough over the Serial Monitor. **Join confirmed successful on real hardware.**
- Turned this into a real git repo at `~/RAK3272S_EdgeNode/` and extended the firmware to send one dummy uplink (incrementing counter byte, `AT+SEND=2:<hex>`) every 5 minutes after join, on top of the working join logic. Compiles clean for the Pico W target.
- Added `docs/RUI3_AT_Command_Manual.md` — an offline mirror of RAKwireless's RUI3 AT Command Manual, so command syntax (e.g. `AT+SEND=<port>:<payload>`) can be checked without needing network access.
- **First real hardware test, end to end.** Flashed via `arduino-cli` UF2 upload over `/dev/ttyACM0`. Boot log showed all AT settings already matched from prior manual testing (skipped re-setting each), OTAA join succeeded (`+EVT:JOINED`), and the first dummy uplink sent (`AT+SEND=2:00` -> `OK`). Cross-checked against ChirpStack's own uplink log (not just the module's local ack): the frame actually arrived — `fPort=2`, `data="AA=="` (0x00), `fCnt=1`, `CRC_OK`, SF12/DR0, RSSI -14dBm, SNR 8.8dB. Pipeline confirmed working end to end (node -> gateway -> ChirpStack -> logger).
- Noticed two pre-existing device-profile issues while checking the ChirpStack log (not caused by this firmware, but worth fixing): the profile's payload codec decodes the raw dummy byte as `{"temp": 22.5}` (misleading — it's not a real reading), and the profile is set to `CLASS_C` while the module is actually configured Class A. Logged in TODO.md.
- Watched several 5-minute cycles live via a small single-open pyserial logger script (background process holding `/dev/ttyACM0` directly, logging to a file) — `arduino-cli monitor` produced no output at all when its stdout wasn't a real TTY, and an earlier two-process `stty`+`cat` capture produced one garbled line (device appeared to echo back a fragment of its own boot banner as if it were typed input) — the single-open script avoided both problems cleanly on every subsequent capture. Confirmed via ChirpStack's own logs that the `LinkADRReq`/`DevStatusReq` downlinks seen on nearly every uplink are normal ADR convergence (RX1-window MAC commands), not a bug — DR climbed from DR0/SF12 to DR5/SF7 within two uplinks given the strong 5m-range signal.
- **Switched to Class C** (production target) per user request. This exposed a real bug in `ensureSetting()`: it compared the expected value via a plain substring search anywhere in the AT response, which false-matched `"C"` against the `C` inside the module's own echoed `"AT+CLASS=?"` query — so it silently skipped sending `AT+CLASS=C` and reported "already C" while the module was still Class A. Fixed by anchoring on the *last* `"AT+<name>="` occurrence (the real value line, which comes after the echoed query) and comparing only the token that follows it, not a substring search over the whole response. Reflashed; module now correctly reports `AT+CLASS=C`, rejoined, and the dummy uplink sent successfully. Uplinks remain unconfirmed (`AT+CFM=0`) for now — confirmed mode is a separate decision, deferred.
- **Pushed to GitHub**, public: https://github.com/Whiteshark-314/RAK3272S_EdgeNode. Before pushing, moved `OTAA_APPEUI`/`OTAA_APPKEY` out of the sketch into a gitignored `secrets.h` (with `secrets.h.example` as a committed template) since the AppKey had been hardcoded in plain text and the repo was going public. Verified with `git check-ignore` that `secrets.h` never got staged, and re-verified after push via the GitHub API that only `secrets.h.example` exists remotely.
- **Replaced dummy-only payload with real sensor data.** `sendDummyUplink()` -> `sendSensorUplink()`: now reads the RP2040's real internal core temperature via `analogReadTemp()`, packed alongside two explicitly-named dummy values (`dummy_humidity_pct`, a sine wave so it visibly changes each send; `dummy_counter`, incrementing) into a 5-byte payload (`int16` temp x100, `int16` humidity x100, `uint8` counter, big-endian). `mcu_temp_c` is the chip's own die temperature, not ambient — named accordingly so it can't be mistaken for a room-temperature reading later.
- The device profile's codec was still the ChirpStack default stub (hardcoded `return {data: {temp: 22.5}}`, ignoring `input.bytes` entirely) — this is what had been producing the misleading `{"temp": 22.5}` on every uplink regardless of payload, explaining the issue noted 2026-08-05. Replaced with a real `decodeUplink()` matching the 5-byte layout above, verified against a Python round-trip test (including a negative-temperature case) before writing it to the device profile in Postgres. First live uplink confirmed correct end-to-end: firmware logged `mcu_temp_c=36.50 dummy_humidity=50.00 dummy_counter=0`, raw hex `0E42138800` matches those values exactly, and ChirpStack decoded the same payload to `{"mcu_temp_c": 36.5, "dummy_humidity_pct": 50, "dummy_counter": 0}`.
